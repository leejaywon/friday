# Friday 하네스 개선 기획 (2026-11-23)

## 원칙 (리서치 근거)

1. **항상 들어가는 컨텍스트는 작게, 나머지는 필요할 때 도구로.** Anthropic context engineering,
   Hermes Agent(항상 주입 ≈3.6k자, 메모리 도구 2개)가 기준. 지금 Friday는 프롬프트만 13.3k자 + 도구 47개.
2. **행동은 프롬프트 규칙이 아니라 메커니즘으로.** 한도는 코드가 강제하고(Claude Code 검색 한도,
   open_deep_research 호출 한도, Jina "beast mode"), 도구 결과가 다음 행동을 안내한다(Anthropic "Writing tools").
3. **규칙은 실제로 관찰된 실패에만, 평가셋으로 검증해서 추가.** 실제 대화 20~50개, 검색해야 하는/안 해야 하는
   경우를 균형 있게(Anthropic evals 가이드). 이번에 만드는 대화 로그가 그 재료가 된다.

## 1. 할 일 등록 확인: 텍스트만 (결정됨)

- add_task / add_reminder / calendar_create_event가 카드를 따로 보내지 않는다(outbox의 *_card 제거).
- 대신 **하네스가 턴 끝에 실제 변경 내역(영수증)을 붙인다**: 실제 도구 호출에서 만든 한두 줄.
  스크린샷처럼 답장엔 4개라고 하고 실제로는 3개만 등록되는 불일치를 사용자가 바로 볼 수 있다. 에이전트는 항목을 다시 나열하지 않는다.
- 알림이 실제로 울릴 때의 ✅/⏳ 버튼은 유지(등록 시점 버튼만 없앰). /tasks, /plan은 그대로.

## 2. 능동 알림: 생성 시 계획 + 하트비트 (결정됨)

- **항목별 알림 계획**: add_task / update_task에 `nudges`(시각 목록)를 추가해 에이전트가 정한다. 생략하면 지금의 기본 규칙.
  발송은 지금처럼 서버 스케줄러가 맡는다(AI가 꺼져 있어도 도착).
- **하트비트**: 하루 몇 번(아침 브리핑 시각, 점심, 저녁) 별도 레인에서 에이전트 턴 1회.
  입력은 오늘 일정, 열린 할 일, 오늘 이미 보낸 알림, 최근 대화 제목뿐.
  할 일은 셋 중 하나: 아무것도 안 함("-"), 메시지 1개, 알림 계획 조정.
  사용자가 고칠 수 있는 HEARTBEAT.md(OpenClaw 방식)에 선호를 적는다.
- **코드가 강제하는 한도**: 조용한 시간, 하루 최대 능동 메시지 수, 최소 간격.
- **캘린더**: 모든 일정에 "N분 전" 알림을 보내던 calendar_loop를 끈다. 구글 자체 알림과 중복이고,
  "9분 전"은 MEETING_LEAD_MIN=10을 60초마다 확인해서 생긴 값이다.
  대신 아침 하트비트가 일정별로 판단한다: 이동 시간, 준비물, 링크처럼 구글이 못 챙기는 것만 맥락을 담은 리마인더로 예약한다.

## 3. 기억과 과거 대화 (Hermes 방식, 예산 고정)

| 항목 | 예산 |
|---|---|
| 항상 주입 | ≈2~3k자: 에이전트가 관리하는 프로필/사실 블록(상한, 사용량 표시) + 최근 대화 5개 제목·날짜 |
| 도구 | 2개: `memory(action…)`(추가/수정/삭제), `recall(query?, thread?, around?, since?)`(기억과 과거 대화 통합 검색 + 스크롤) |
| 검색 1회 결과 | ≈3~4k자: 상위 5건 × 300자 스니펫, 1등만 앞뒤 3~5개 메시지 펼침, 메시지당 1,000자 |

- **저장**: 모든 텔레그램 턴(사용자 말, 답장, 출처 링크)을 SQLite에 저장하고 FTS5 `trigram`으로 색인.
  trigram은 3자 미만 단어를 못 찾으므로 "제품" 같은 2음절 단어는 LIKE로 보완.
- **요약**: 대화가 닫힐 때(6시간 무응답, /new) 싼 모델 1회로 제목, 2~4줄, 핵심 개체(제품명 한/영)를 써서 검색 가능한 행으로 저장. 검색할 때는 LLM 호출 없음.
- **빼는 것**: "최근 기억 20개" 주입(최신이 곧 관련 있는 것은 아니고, 크기도 무한정), 임베딩, 자동 회상 서브에이전트(지연이 큼).
  임베딩은 평가셋에서 실제로 놓치는 경우가 보일 때 다국어 모델(bge-m3 등)로 추가.
- 웹 리서치 결과도 대화 로그에 출처와 함께 남으므로 "CCTV 뭐 봤지?"는 recall 한 번으로 찾는다.

## 4. 웹 리서치: 규칙표 대신 메커니즘

- **프롬프트**: 흩어진 규칙("카페 빼고", "최소 두 번 더")을 원칙 몇 줄로 바꾼다.
  답이 최신·지역·구체 사실에 달렸을 때 검색, 넓게 시작해 좁히기, 1차 출처와 날짜,
  구체 정보는 스니펫 말고 페이지를 읽기, 브라우저는 JS·로그인·조작이 필요할 때만,
  새 정보가 안 나오면 멈추고 확인 못 한 것과 시도한 것을 말하기.
- **코드**: codex app-server가 webSearch 이벤트를 주므로(codex_server.py:70) 턴마다 검색 수를 센다.
  넉넉한 소프트 한도에서 기존 "[Friday supervisor]" 노트로 "가진 걸로 답하거나 부족한 걸 말해"를 보내고, 하드 한도에서 답을 강제한다. Claude 엔진은 WebSearch tool_use 수로 센다.
- **도구 결과가 안내**: browser_find 결과가 비었을 때나 페이지가 얇게 읽힐 때 다음 수를 도구 응답에 적는다.
- **큰 리서치**: 코딩 작업 방식(진행 표시, 중지 버튼, 부분 결과)을 재사용한 백그라운드 리서치. 2단계 이후.

## 5. 컨텍스트 다이어트

- CAPABILITIES(7.3k자)는 대부분 도구 설명과 중복이다. 사용법은 각 도구의 docstring으로 옮기고 프롬프트에는 언제 무엇을 쓰는지만 남긴다.
- 목표: 고정 프롬프트 ≈6k자 이하. 메모리 도구 4개를 2개로 합쳐 도구 수도 줄인다.

## 6. 평가

- 새 대화 로그에서 실제 대화 20~50개를 뽑는다. 검색 필요/불필요, 과거 회상, 할 일 등록, 알림 판단이 고루 섞이게.
- 결과 기준 LLM 채점(정확성, 출처, 효율)에 대화 기록 직접 읽기를 병행하고, 홀드아웃을 둔다.
- 단위 테스트는 꼭 필요한 것만.

## 결정 사항 (2026-11-23)

- 기존 미커밋 변경(브라우저 필요할 때만 붙이기 + 웹 안내 문구)은 그대로 별도 커밋. 웹 문구는 4단계에서 다시 씀.
- 등록 확인: 카드 없이 텍스트. 하네스가 실제 도구 호출로 만든 영수증을 답장 끝에 붙임.
- 캘린더 "N분 전" 알림: 1단계에서 바로 끔. 아침 브리핑은 유지.
- 진행: 단계마다 테스트, 커밋, push 후 배포 여부를 물어봄.

## 순서

1. 텍스트 확인 + 영수증 + calendar_loop 끄기 (작음)
2. 대화 로그 + recall/memory 통합 + 대화 요약 + 항상 주입 블록
3. 알림 계획(nudges) + 하트비트 + 한도
4. 웹 원칙 정리 + 검색 수 한도 + 프롬프트 다이어트
5. 평가셋 (2번 이후 로그가 쌓이면)
