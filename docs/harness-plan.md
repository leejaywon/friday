# Friday 하네스 기획: 범용 태스크 에이전트 (2026-11-23, 개정)

## 문제 (사용자 제시)

1. "이거 해야 돼"라고 하면 Done / Tomorrow / Remove 버튼 카드가 바로 떠서 보기 싫다.
2. heads-up이 한 번 오고 끝난다. 얼마나 자주 리마인드할지 AI가 그때그때 판단해야 한다.
3. 과거 대화("우리 CCTV 뭐 봤었지?")를 어떻게 가져오고 기억할지가 엉망이다.
4. 구글 캘린더 일정마다 9분 전 알림이 온다. 보고 알리기만 하는 멍청한 방식이면 안 된다.
5. 웹서핑을 언제, 어떻게, 얼마나 시도할지 모른다.

다섯 개 모두 하네스 문제다. Friday는 범용 태스크 에이전트여야 한다. 그래서 증상마다 기능을 붙이지 않고
(할 일 전용 알림 필드, 캘린더 전용 판단, 웹 전용 규칙표 같은 것), 어떤 일에도 쓰이는 메커니즘 몇 개로 해결한다.
일의 크기와 종류는 매번 달라지고, 하네스가 할 일은 그 일에 맞는 컨텍스트, 도구, 흐름을 주는 것이다.

## 원칙 (리서치 근거)

- 항상 들어가는 컨텍스트는 작게, 나머지는 필요할 때 도구로 (Anthropic context engineering; Hermes Agent는 항상 주입 ≈3.6k자, 기억 도구 2개).
  지금 Friday는 고정 프롬프트 13.3k자 + 도구 47개.
- 행동은 프롬프트 규칙이 아니라 메커니즘으로: 한도는 코드가 강제하고(Claude Code 검색 한도, open_deep_research 호출 한도),
  도구 결과가 다음 수를 알려준다(Anthropic "Writing tools for agents").
- 프롬프트는 "적절한 고도"의 원칙만. 사례별 if-else 금지("카페 빼고 다시" 같은 문구).
- 규칙은 실제 실패에서만, 평가셋에서 나아질 때만 추가(Anthropic evals: 실제 사례 20~50개).

## 메커니즘

### A. 에이전트의 말이 곧 UI  → 문제 1
- 도구는 스스로 카드나 버튼을 보내지 않는다. 등록·변경 확인은 에이전트 답장이 한다. (완료: 등록 카드 제거)
- 버튼은 사용자의 탭이 정말 필요한 곳에만: 승인, 폼, 알림이 실제로 울릴 때의 ✅/⏳.

### B. 스스로 깨우기 (wake-up)  → 문제 2, 4
- 범용 도구 하나: `wake(when, note)`. 지정 시각에 에이전트 턴이 note와 함께 다시 돈다.
  그때 상황을 보고 메시지를 보낼지, 다시 예약할지, 아무것도 안 할지 판단한다.
- 같은 도구로 다음을 모두 처리한다(전부 예시일 뿐, 별도 기능이 아님):
  - 할 일을 몇 번, 언제 다시 챙길지
  - 회의 전에 링크나 준비물, 이동 시간을 챙길지
  - 아까 막힌 일을 나중에 다시 시도할지
- 하트비트도 반복 wake일 뿐이다. 정해진 시각에 오늘 일정, 열린 일, 예정된 wake, 최근 대화 제목을 보고 판단한다.
- 리마인더(정해진 시각에 정해진 문구)는 지금처럼 서버가 AI 없이 확실히 보낸다.
- 코드가 강제: 조용한 시간, 하루 최대 능동 메시지 수, 최소 간격, 예약할 수 있는 wake 개수.
- 캘린더 "N분 전" 루프는 제거(완료). 일정 판단은 하트비트/wake가 한다.

### C. 일화 기억  → 문제 3
- 모든 대화 턴(사용자 말, 답장, 출처 링크)을 SQLite에 저장. 검색은 FTS 없이 단어 포함 스캔(조사 제거).
  2음절 한국어도 찾고, 메시지 6만 개(몇 년치)에서 160ms 이하로 측정됨. 느려지면 그때 FTS5 trigram.
- 대화가 닫힐 때(무응답 6시간, /new) 싼 모델 1회로 제목, 2~4줄 요약, 핵심 개체(한/영)를 쓴다.
- 도구 2개: `memory`(오래 갈 사실 추가/수정/삭제), `recall`(기억과 과거 대화 통합 검색, 대화 스크롤).
  검색 1회 결과 ≈3~4k자(상위 5건 × 300자, 1등만 앞뒤 메시지 펼침). 검색할 때 LLM 호출 없음.
- 임베딩, 자동 회상 서브에이전트는 넣지 않는다. 평가셋에서 실제로 놓치는 게 보이면 추가.

### D. 노력 조절과 멈춤  → 문제 5 (웹 포함 모든 긴 작업)
- 기존 supervisor(실패·정지 감시)를 일반화: 같은 종류의 시도가 새 정보 없이 반복되면 체크포인트 노트를 넣는다.
  "지금 찾은 것 / 부족한 것 / 계속할지"를 정하게 한다.
- 넉넉한 하드 한도는 코드가: 턴당 도구 호출 수와 시간. 넘으면 가진 걸로 답하고 못 한 것을 말하게 강제한다.
  웹 검색도 이 중 하나로 센다(codex app-server의 webSearch 이벤트).
- 도구 결과가 다음 수를 안내: 빈 결과, 얇은 페이지, 실패한 클릭.
- 프롬프트에는 원칙 몇 줄만: 최신·구체 사실은 찾아보고, 넓게 시작해 좁히고, 1차 출처를 쓰고,
  브라우저는 JS·로그인·조작이 필요할 때, 새 정보가 없으면 멈추고 무엇을 시도했는지 말한다.

### E. 컨텍스트 다이어트 (모든 문제의 바탕)
- 고정 프롬프트는 원칙과 안전 규칙만. 도구 사용법은 각 도구 설명으로 옮긴다.
  긴 사용 설명(브라우저, 오디오, 폼)은 그 도구 묶음을 붙일 때만 보이게 한다.
- 목표: 고정 프롬프트 ≈5~6k자, 항상 주입 기억 ≈2~3k자.

### F. 평가
- C의 대화 로그에서 실제 대화 20~50개를 뽑아 평가셋을 만든다. 범위: 검색 필요/불필요, 회상, 할 일, 능동 알림 판단.
- 결과 기준 LLM 채점에 기록 읽기를 병행하고 홀드아웃을 둔다. 단위 테스트는 꼭 필요한 것만.

## 결정 사항

- 다음 단계: C 일화 기억.
- 하트비트: 깨어 있는 동안 3~4시간마다. 아침 브리핑은 첫 하트비트가 대신한다.
- 능동 메시지 한도: 느슨하게. 조용한 시간 02:00~07:00만 두고 개수 제한은 없다.
  사용자가 예약한 리마인더는 한도와 상관없이 항상 간다.
- 할 일 고정 알림: 09:00 / 1시간 전 heads-up은 없애고 wake가 맡는다. 마감 시각 알림은 안전망으로 남긴다.
